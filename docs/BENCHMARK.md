# 性能压测报告

> 数据采集时间：2026-11-19　｜　代码版本：主从 Reactor + WebSocket 长连接

## 1. 测试环境

| 项 | 值 |
| --- | --- |
| 运行环境 | WSL2 / Ubuntu 24.04 |
| CPU | 8 vCPU（宿主 Intel Core Ultra 7 155H） |
| 内存 | 8 GB |
| 编译器 | g++ 13.3，Release（-O2 + -Wall -Wextra） |
| 网络 | 本机 loopback（客户端与服务端同机） |
| 依赖 | Redis 7（本机） |

**重要前提**：压测客户端和服务端跑在同一台机器、抢同样的 8 个核，所以下表的
"服务端 CPU 核数"是可信的，而绝对吞吐会低于裸金属两台机器的结果。所有数据
只用于横向比较（不同从 Reactor 数量、优化前后），不代表生产环境的绝对上限。

## 2. 为什么不用 wrk 压 WebSocket

wrk 只会说 HTTP，握手完就不会发帧了。所以：

- **HTTP 路径**（静态页）用 `wrk`；
- **WebSocket 聊天路径**用仓库里的 `tools/bench.cpp` 自研压测客户端。

压测客户端的设计要点（也踩过坑）：

1. **不能用"一条连接一个线程"**。100 条连接就是 100 个线程，在 8 核机器上
   客户端自己就会因为线程调度把 RTT 抬高一个数量级，测出来的是客户端的
   调度延迟，不是服务端能力。改成少量线程 + epoll 管全部连接。
2. **不能死等 `login_ok`**。第一版用阻塞 socket 死循环 `recv`，服务端回
   `error`（例如限流）时客户端永远等下去。改成非阻塞 + `poll` 超时。
3. 每条连接维护一个 32 深的在途窗口，用"自己发出的消息被广播回来"计算端到端
   RTT，消息文本带唯一序号，按序号回填时间戳。

## 3. 结果

### 3.1 连接建立（1000 条长连接）

| 从 Reactor | 连接数 | 建立+登录耗时 | 失败 |
| --- | --- | --- | --- |
| 4 | 1000 | 0.55 s（≈1800 连接/s） | 0 |
| 8 | 1000 | 0.42 s（≈2400 连接/s） | 0 |

每条连接都完整走完 WebSocket 握手 + `SET chat:online:<name> NX EX` 的 Redis 校验。

### 3.2 可持续负载下的延迟

200 条长连接，每条每秒 20 条消息 = **4000 msg/s**，广播扇出 **80 万帧/秒**。

| 从 Reactor | P50 | P90 | P99 | Max | 服务端 CPU | 失败 |
| --- | --- | --- | --- | --- | --- | --- |
| 4 | 5.91 ms | 15.53 ms | **22.43 ms** | 29.69 ms | 2.70 核 | 0 |
| 8 | 4.66 ms | 14.67 ms | 24.66 ms | 54.70 ms | 2.75 核 | 0 |

结论：4000 msg/s 的广播负载在 8 核机器上是很轻松的档位，P99 在 22–25 ms。
从 4 增到 8 个 Reactor，P50 略降但 P99 抖动变大（线程更多，调度抖动更大）。

### 3.3 吞吐与扩展性（200 连接，不限速压到饱和）

| 从 Reactor | 消息吞吐 | 扇出帧吞吐 | 服务端 CPU |
| --- | --- | --- | --- |
| 1 | 367 msg/s | 76,037 帧/s | 1.03 核 |
| 2 | 1,472 msg/s | 285,279 帧/s | 2.06 核 |
| 4 | 6,644 msg/s | 1,209,482 帧/s | 4.07 核 |
| 8 | **9,407 msg/s** | **1,756,063 帧/s** | 5.24 核 |

- 单 Reactor 封顶在 1 个核、7.6 万帧/秒——符合"一个 epoll 线程"的预期；
- 1 → 8 个 Reactor，扇出吞吐提升 **23 倍**，CPU 只增加到 5.24 核；
- 8 Reactor 没有吃满 8 核，说明瓶颈已经从 Reactor 转移到别处
  （跨 Reactor 的投递、调度、以及同机压测客户端的干扰）。

### 3.4 1000 长连接下的广播（低速发送）

1000 条连接，每条每秒 1 条 = 1000 msg/s，扇出 **106 万帧/秒**（已接近饱和）：

| 指标 | 值 |
| --- | --- |
| P50 | 88.06 ms |
| P99 | 618.16 ms |
| 服务端 CPU | 3.81 核 |
| 失败连接 | 0 |

说明：这个档位已经压到系统上限，延迟被排队主导。1000 人同时在线的群聊，
每条消息要写 1000 个 socket，这是广播模型的固有成本，不是 bug。

### 3.5 HTTP 静态页（wrk）

```
wrk -t4 -c200 -d10s http://127.0.0.1:8888/
Requests/sec:  84,128
Latency p50:   1.31 ms
Transfer/sec:  1.17 GB
```

注意：这是"短连接 + 每次返回 14.8KB 首页"的极限值，衡量的是
accept → HTTP 解析 → send → close 这条链，**不代表聊天路径的性能**。

## 4. 一次真实优化：广播投递批量化

压测第一版发现：8 个从 Reactor 只吃到 4.97 个核，吞吐上不去。定位到
`ChatServer::broadcast`：

```cpp
// 优化前：每条连接投递一次
for (auto &conn : targets) conn->postSend(payload);
```

一条消息要产生 N 次跨线程任务、N 次 mutex、N 次 eventfd 写唤醒。
广播扇出到 200 人时，光是"投递"本身就成了瓶颈。

改成**按 Reactor 分桶**，一条消息对每个从 Reactor 只投递一个任务：

```cpp
std::vector<std::vector<ConnectionPtr>> byLoop(ioPool_->size());
// ... 按 conn->loopIndex() 分桶
for (size_t i = 0; i < byLoop.size(); ++i) {
    ioPool_->get(i)->runInLoop([conns = std::move(byLoop[i]), payload] {
        for (auto &conn : conns) conn->send(payload);
    });
}
```

同时把 `queueInLoop` 的 eventfd 唤醒去重（队列非空时不再重复唤醒）。

优化前后（200 连接，不限速）：

| 从 Reactor | 优化前 | 优化后 | 提升 |
| --- | --- | --- | --- |
| 4 | 4,225 msg/s | 6,644 msg/s | **+57%** |
| 8 | 5,668 msg/s | 9,407 msg/s | **+66%** |

服务端 CPU 几乎没变（3.95→4.07、4.97→5.24 核），等于**同样的 CPU 多干了 60% 的活**。

## 5. 可以直接写进简历的表述

> 基于 Epoll 主从 Reactor 自研 WebSocket 聊天服务器：单机 8 核支撑 1000 条长连接；
> 200 连接、4000 msg/s 广播负载下 P99 22ms；消息扇出峰值 176 万帧/秒。
> 通过"按 Reactor 批量广播 + eventfd 唤醒去重"优化消息投递路径，4/8 从 Reactor
> 吞吐分别提升 57% / 66%。

## 6. 这套数据不能证明什么

写清楚边界，面试时反而加分：

- **不是裸金属**：WSL2 与 Windows 共享 CPU，绝对数字偏低；
- **客户端同机**：压测客户端占用 20%–45% 的 8 核，与服务端抢资源；
- **RTT 含排队**：广播模型下，P99 里有一部分是"前面还有几十条消息在排队"，
  不等于网络往返；
- **没有测长时间稳定性**：没跑过 24 小时，内存曲线未验证；
- **没有测弱网**：丢包、高延迟、半开连接（keepalive 之外）都没覆盖。

下一步如果要更硬的数据：两台机器（服务端独占 8 核，客户端用另一台），
或者把客户端放到宿主机、服务端单独绑核。
